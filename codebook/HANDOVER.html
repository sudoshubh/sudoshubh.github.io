Multi-Reason: teaching an AI model to reason in Indian languages

This page explains the project to the student taking it over: what it is, what has been finished, what is still open, and where to go next. Read it top to bottom once, then use it as a reference.

Handed over by Shubham Sharma (M25AI2024) Supervisor Dr. Deeksha Varshney Status as of 16 Nov 2026

What this project is

Most AI language models are good at English and much weaker in languages like Hindi, Punjabi and Marathi. One reason is that there is very little training data in these languages that shows how to solve a problem step by step.

In this project we did three things:

  • Made the data. We used bigger AI models (Google Gemini and gpt-oss-120b) to write step-by-step solutions for multiple-choice exam questions, in four languages: Hindi, English, Punjabi and Marathi.
  • Trained a smaller model on it. We took an open 7-billion-parameter model (DeepSeek-R1-Distill-Qwen-7B) and taught it, using a cheap training method called LoRA, to write its reasoning and then give the answer.
  • Tested it. We checked how often the trained model picks the right answer, on our own held-out questions and on the official MMLU-Hindi benchmark that other research groups use.

How it works, start to end

The whole project is a chain of four steps. Each step has its own script, and each step's output is the next step's input.

Make reasoning data

A big model reads each question and writes its thinking inside <think> and the final letter inside <answer>.

cot_mmlu_gemini*.py, generate_reasoning_chains.py

Split the data

Divide into train, validation and test. Test questions must never appear in training.

generated_data/mmlu/data/data_split_multilingual/

Fine-tune the model

Train the 7B model with LoRA on the training split. Takes about 10 to 25 hours on one 11 GB GPU.

finetune_multilingual.py

Test and score

The model answers each test question. A parser pulls out the letter and compares it with the correct one.

test_multilingual.py, evaluation.py

How the Hindi reasoning data was made (the "4-cycle" method)

  • Cycle 1: Gemini answers each Hindi question and explains its thinking. It is not shown the correct answer. 92% of questions were solved here.
  • Cycles 2 and 3: Only the questions it got wrong are asked again. This time Gemini sees its own earlier wrong attempt and tries again, still without the answer.
  • Cycle 4: For the few still wrong, Gemini is given the correct answer and writes an explanation for it.
  • The wrong attempts plus the final right one, joined by the word "Wait", make the multi-chain data. Only the final right attempt makes the single-chain data.

English, Marathi and Punjabi reasoning was written in one pass by gpt-oss-120b, with no correction cycles.

Getting started

Server: shared lab machine with 7 GPUs (NVIDIA RTX 2080 Ti, 11 GB each). Other students use it too, so always check which GPUs are free with nvidia-smi before starting a job.

Project folder: /Data/deeksha/shubham/multi-reason/multi-reason

Python environment: the conda env called finetune (it has Unsloth, TRL and PyTorch with CUDA). The .venv folder inside the repo is a Windows environment and will not work here.

Train the model

# pick a free GPU number, here GPU 1
CUDA_VISIBLE_DEVICES=1 /Data/deeksha/miniconda3/envs/finetune/bin/python \
    finetune_multilingual.py > logs_my_run.txt 2>&1 &

# watch progress
tail -f logs_my_run.txt

Checkpoints are saved inside qwenModel/finetune_multilingual_results_v2/. Change output_dir in the script before a new run so you do not overwrite the old ones.

Test the model (split across GPUs to go faster)

# each GPU takes a slice of the 644 test questions
CUDA_VISIBLE_DEVICES=1 python test_multilingual.py --model_path <checkpoint> \
    --start 0   --end 322 --output evaluation/my_run_0_322.csv &
CUDA_VISIBLE_DEVICES=5 python test_multilingual.py --model_path <checkpoint> \
    --start 322 --end 644 --output evaluation/my_run_322_644.csv &

# join the slices back into one file
python merge_shards.py evaluation/my_run_0_322.csv evaluation/my_run_322_644.csv \
    --output evaluation/my_run_merged.csv

Score the answers

Open evaluation.py, put your merged CSV in the FILES list near line 127, and run it. It prints the accuracy and writes two extra files ending in _correct.csv and _incorrect.csv so you can read the mistakes.

Run on the official benchmark

CUDA_VISIBLE_DEVICES=<n> python benchmark_generative.py \
    --model_path <checkpoint> --dataset mmlu --limit 15 --verbose   # quick check first
CUDA_VISIBLE_DEVICES=<n> python benchmark_generative.py \
    --model_path <checkpoint> --dataset arc --start 0 --end 600 \
    --output evaluation/gen_v2_arc_shard0.csv

The full MMLU-Hindi run (12,437 questions) took several days split over 3 GPUs. score_gen_mmlu.py merges and scores those shards.

What is done

Reasoning dataset in four languages

1,638 Hindi questions with checked reasoning from the 4-cycle method, plus Punjabi, English and Marathi versions. Split into 5,124 train, 645 validation and 644 test rows. We checked that none of the 644 test questions appear in training.

First training run (v1)

Accuracy went from 30.9% to 46.3%. Later we found a bug: the script used the wrong "chat template" (the text format the model expects). The model never properly learned when to stop writing.

Fixed training run (v2)

Retrained using the model's own format. We also found that a library function, apply_chat_template(), quietly deletes the reasoning part from training text, so we build the text by hand instead. Final accuracy 45.8%, about the same as v1.

Comparing training styles

Compared "answer only", "single reasoning chain" and "multi-chain with Wait" training, on both Llama-3.1-8B and the DeepSeek 7B model. Reasoning helped Llama by about 9 points on Hindi.

Data leakage check

Found that in an older test set, 648 of 656 test questions were also in the training data, so those older scores are too high. Built a new clean multi-chain dataset (4,615 train rows) with zero overlap and retrained on it. It scored 39.8%, lower than v2, mainly because long answers ran out of space before reaching the answer.

Official MMLU-Hindi benchmark

Ran v2 on all 12,437 questions, letting it write its reasoning first. It got 5,661 right: 45.52% (±0.88). That is almost the same as our own 644-question test (45.8%), so the result holds at full scale. Only 33 answers (0.3%) had no readable letter. It beats every published baseline we compare against except Gemma-2-9B (47.16%). Results are in evaluation/gen_v2_mmlu_full_merged.csv.

The other models were mostly scored by a different method (log-likelihood, which picks the option the model finds most likely, without letting it write reasoning). Things to be careful about

These cost us days of work. Please read them before changing any script.

The model is not "Qwen2.5-1.5B"

Many file names say Qwen2.5-1.5B, but the model in qwenModel/ is really DeepSeek-R1-Distill-Qwen-7B. Check qwenModel/config.json. The models/ folder with Llama is old and not used any more.

Use the model's own chat template

Older scripts call get_chat_template(..., "qwen-2.5"). That is wrong for this model and caused v1's bug. The correct markers are <｜User｜>, <｜Assistant｜> and the stop token <｜end▁of▁sentence｜>.

Reasoning silently disappears in training

tokenizer.apply_chat_template() removes everything inside <think> from the answer. If you use it for training text, the model learns no reasoning at all, with no error shown. Build the text by hand, as in finetune_multilingual.py.

Check for leaked test questions

The older data_split_wait and data_split_single_cot folders have test questions that are also in training. Scores on those (like the 90.7% "answer only" result) mean memorising, not learning. Use data_split_multilingual for honest numbers.

Lower loss does not mean better

v2's step 1,000 had lower validation loss but scored 39.3%, while the final checkpoint scored 45.8%. Pick checkpoints by running the test, not by looking at loss.

Shared GPUs and disk

Another user's job can take a GPU you thought was free, and the shard will crash with "dispatched on the CPU or the disk". A full disk once crashed training at step 600. Keep save_total_limit=2 in training and check df -h.

Secret keys in code

model_download.py, test_llama_generic.py and wait_then_run_pa_reasoning.sh have API keys written inside them. Move these to environment variables and ask for new keys. Never push these files to a public place.

Some result files are broken

multi_llama3.1_1B_*.csv is corrupted and multi_llama3.2_3B_*.csv is incomplete (1 of 656 rows). Do not use them. Also, 38 Punjabi training rows have empty reasoning and are not removed by the training script.

Do first

Self-consistency test: v1 vs v2

Self-consistency means asking the model 5 times and taking the most common answer. v1's bug showed up mostly in this setting (66.5% of answers got stuck repeating). We have never run v1 and v2 side by side this way, so we cannot yet say the fix helps.

Scripts exist: self_consistency_multilingual.py. Check that it uses the model's own template before running.

Next

Re-test the multi-chain model with more room

The clean multi-chain model scored 39.8%, but 62 of 644 answers ran out of space (4,096 tokens) before giving an answer. Re-test with a bigger limit, for example 8,192, and see if it overtakes v2.

Checkpoint: qwenModel/finetune_multichain_results/checkpoint-3462.

Next

Measure language mixing in Punjabi and Marathi

In some answers the model starts reasoning in Punjabi or Marathi and switches to English halfway. We saw this in examples but never counted it. Write a small script that checks what share of each answer is in the right script (Gurmukhi or Devanagari).

Use the _incorrect.csv and _correct.csv files from v2 final.

If time allows

Explain why self-consistency scored lower

On the older test set, 5-vote majority (50.8%) scored below a single answer (57.8%). Only 79% of those answers closed the answer tag. The cause is not known yet, and the old script may have used the wrong template and checkpoint.

If time allows

Clean up the repository

Add a requirements.txt, remove secret keys, move old Llama scripts into an old/ folder, and fix Windows paths still present in parts of evaluation.py.

Future scope

  • More data for Punjabi and Marathi. These two improve the least and have the least data. Running the same 4-cycle correction method for them, instead of one pass, may help.
  • Keep reasoning in the same language. Add a check that removes training examples which switch to English, or reward the model for staying in one language.
  • Shorter reasoning. Very long answers hit the length limit and lose the answer. Training on shorter, cleaner chains could fix this and also make the model faster.
  • More languages. Bengali data already exists in the multi-chain set. Tamil, Telugu and Gujarati are natural next steps, and the pipeline can be reused as is.
  • Reinforcement learning. Instead of only copying good examples, reward the model when its final answer is right (methods like GRPO). This is how many recent reasoning models were trained.
  • Other benchmarks. Try IndicMMLU-Pro and other Indian-language tests to show the model works beyond MMLU and ARC.
  • Fair comparison with Nanda. Llama-3-Nanda-10B was scored with a different method. Scoring both models the same way would make the comparison fully fair.

Word list

Chain of thought (CoT)
The model writes its step-by-step thinking before giving the answer.
Reasoning chain
One written attempt at solving a question, from start to answer.
Multi-chain / "Wait"
Training text with earlier wrong attempts, then "Wait", then the right attempt. It teaches the model to correct itself.
Fine-tuning
Training an existing model a bit more on our own data.
LoRA
A cheap way to fine-tune: only a small add-on (about 0.5% of the model) is trained, so it fits on an 11 GB GPU.
4-bit loading
Storing the model in a compressed form to save GPU memory.
Checkpoint
A saved copy of the model at some point during training.
Chat template
The exact text format the model expects, with special markers for "user", "assistant" and "stop".
Token
A small piece of text, roughly a word or part of a word. Length limits are counted in tokens.
Validation loss
A number training reports to show how well the model fits unseen data. Lower is usually better, but not always, as we found.
Data leakage
When test questions are also in the training data, so the test score is too high.
Shard
A slice of the test set run on one GPU, so many GPUs can work at the same time.
Self-consistency
Asking the model the same question several times and taking the most common answer.
Code-switching
When the model changes language in the middle of its answer.
MMLU / ARC
Well-known multiple-choice exam benchmarks. We use their Hindi versions from alexandrainst/m_mmlu and alexandrainst/m_arc.
NO_MATCH
The scorer could not find any answer letter in the model's output.
